작성일 2026-08-30. 사전지식 없이 읽을 수 있게 썼다. 용어는 처음 나올 때 풀어서 설명한다.

## 1. 이게 뭐 하는 물건인가

**코드를 넣으면, 암호를 잘못 쓴 자리를 찾아 보고서로 내주는 검사 도구다.**

- 입력: GitHub 주소 또는 내 컴퓨터의 프로젝트 폴더
- 출력: SARIF 보고서 (보안 검사 결과의 국제 표준 파일 형식. GitHub에 올리면
  "이 파일 몇째 줄이 위험합니다"가 화면에 자동 표시된다)

"암호를 잘못 쓴 자리"란 이런 것들이다:

- 깨진 지 오래된 해시함수(MD5, SHA-1)로 비밀번호를 저장하는 코드
- 너무 짧은 암호키(RSA 1024비트)를 만드는 코드
- 소스코드에 비밀키를 그대로 박아둔 코드 (코드를 보는 사람 모두가 열쇠를 갖게 됨)

특징은 **판정마다 "국가 표준문서 몇 쪽에 그렇게 적혀 있다"는 근거가 붙는다**는 것.
"이거 위험해요"가 아니라 "KISA 안내서 9쪽 표에 따르면 RSA는 2048비트
이상이어야 하는데 이 코드는 1024비트입니다"라고 말한다.

## 3. 검사가 돌아가는 순서

명령 한 줄이 이 순서로 돈다:

```
저장소 받기 → 암호 쓰는 자리 찾기 → 값 추적 → 표와 비교 → (LLM 판정) → 보고서
```

풀어서:

1. **받기** — git clone. 어느 커밋을 검사했는지 해시를 기록 (나중에 "이 보고서가
   어느 시점 코드에 대한 것인지" 증명용)
2. **자리 찾기** — 코드를 문법 단위로 분해해서(tree-sitter라는 도구)
   `Cipher.getInstance(...)` 같은 암호 API 호출을 전부 찾는다. 글자 검색(grep)이
   아니라 문법 분해라서 주석이나 문자열 속 단어에는 안 속는다
3. **값 추적** — `Cipher.getInstance(algo)` 처럼 값이 변수에 들어 있으면, 그 변수가
   어디서 왔는지 거꾸로 따라간다. 같은 함수 안 → 클래스 필드 → 이 함수를 부르는
   다른 파일까지. **끝까지 못 찾으면 "모른다"고 남긴다. 절대 추측하지 않는다**
4. **표와 비교** — 찾은 값을 표준문서에서 뽑아둔 숫자 표와 비교한다.
   "RSA 1024비트 < 기준 2048비트 → 미달" 같은 계산. 여기서 안전하다고 판명나면
   LLM을 부르지도 않고 끝낸다
5. **LLM 판정 (선택)** — 표로 판정이 안 서는 자리만 LLM이 주변 코드를 읽고
   "이 줄이 실제 암호 연산인지 / 그냥 알고리즘 이름 목록인지 / 테스트 데이터인지"를
   판정한다. **LLM은 이 역할 판정만 한다. 숫자 비교, 위치, 규칙 번호는 절대 안 맡긴다**
6. **보고서** — 코드가 SARIF를 조립한다. 위반은 `fail`, 판정 못 내린 건 버리지 않고
   `review`(사람이 확인할 목록)로 내보낸다

## 4. config/ — 사람이 관리하는 지식

이 폴더가 이 시스템의 "법전"이다. 코드 수정 없이 여기만 고쳐도 검사가 달라진다.

**tier1_rules.json — 검사 규칙 7개.**
규칙마다 "어떤 호출/문자열이 나오면 의심하라"(트리거), CWE 번호(취약점 국제 분류
번호), 심각도, 수정 안내가 적혀 있다. 새 유형을 잡고 싶으면 여기에 규칙을 추가한다.

**threshold_tables.json — 표준문서의 어느 표를 믿을지 사람이 지정한 지도.**
PDF의 표들은 목적이 제각각이라(같은 SHA-256도 "전자서명용" 표와 "메시지인증용"
표에서 기준이 다르다) 자동으로 긁으면 틀린다. 실제로 자동으로 긁었더니 "RSA가
최고 등급 보안강도를 만족한다"는 엉터리 행이 나왔다. 그래서 **어느 문서 몇 쪽의
어느 표를 어떤 용도로 읽을지 사람이 한 칸씩 지정**했고, 읽을 수 없는 표 3개는
이유를 적어 제외했다.

**tier1_thresholds.json — 위 지도로 표에서 뽑아낸 숫자 기준표 82행. (자동 생성물)**
`python tools/build_thresholds.py` 가 만든다. 직접 수정 금지 — 지도를 고치고 재생성.

**value_corrections.json — OCR이 반복해서 잘못 읽는 값의 수동 보정 목록.**
스캔 PDF에서 SHA3-384를 자꾸 SHA3-284로 읽는 식의 오류를, 사람이 원문과 대조해
확정한 값으로 덮어쓴다. 보정마다 근거가 적혀 있다.

**config.*.json — 모델 이름, 경로 같은 실행 환경 설정.**

## 6. 설계 원칙 — 왜 이렇게 만들었나 (사고 사례와 함께)

이 시스템은 실패를 겪을 때마다 원칙을 하나씩 세웠다. 원칙을 모르고 고치면
같은 사고가 재발한다. 상세한 것은 판정-근거.md, 여기엔 요지만.

**원칙 1. 재는 것은 코드가, 판단은 LLM이.**
"RSA 2048비트면 충분한가"를 LLM에 물으면 기억으로 답하다 틀린다. 숫자 비교는
코드가 표를 보고 하고, LLM에는 계산이 끝난 결과를 사실로 준다. LLM에 남는 질문은
"이 코드가 무엇에 쓰이는가"뿐이다. (측정: 표가 재준 판정 90건을 LLM이 하나도
뒤집지 않았다. 분업이 실제로 작동한다는 뜻)

**원칙 2. 값을 못 봤으면 어느 쪽으로도 판정하지 않는다.**
사고: 값을 못 찾은 자리에서 LLM의 "위반" 답만 되돌리고 "정상" 답은 받았더니,
하드코딩된 키 22건이 소리 없이 사라졌다. LLM은 못 본 것을 정상이라고 답한
것이다. 지금은 위반이든 정상이든 채택하지 않고 "확인 필요"로 사람에게 넘긴다.

**원칙 3. 정답이 하나인 질문에 유사도 검색을 쓰지 않는다.**
사고: "이 함수를 부르는 곳"을 이름만으로 느슨하게 찾았더니, 다른 파일의 동명
함수 값이 흘러들어 IV(암호 초기값) 인자에 `RC4`와 `http://www.google.com`이
들어왔다. 값이 하나 틀리면 판정이 뒤집힌다. 구조로 답할 수 있는 질문은 반드시
구조(문법 분해, 정확한 색인)로 답한다.

**원칙 4. 검색(RAG)은 근거 인용에만 쓰고, 탐지를 촉발하지 않는다.**
검색 결과가 판정에 입력되는 경로가 코드에 아예 없다. 검색이 틀려도 판정은 안
바뀌고 인용문만 나빠진다.

**원칙 5. 같은 입력이면 바이트까지 같은 보고서.**
정적 분석 도구는 이래야 CI(자동 빌드 검사)에 붙일 수 있다. LLM 포함 세 경로
모두 두 번 돌려 파일이 완전히 같음을 확인했고, 테스트로 고정돼 있다.
**보고서에 시각 넣지 말 것. LLM 온도 켜지 말 것. 정렬 건드릴 때 조심할 것.**

**원칙 6. 확신도 퍼센트를 싣지 않는다.**
LLM이 신고하는 확신도는 늘 0.95라 아무것도 구분 못 했다. 대신 "값이 코드에서
확정됐는가 / 근거 조항이 검수를 거쳤는가"라는 검증 가능한 사실을 싣는다.

## 8. 다음 사람이 할 일 (효과 큰 순)

**1. 검사 규칙 5종 추가** — 고정 솔트, 예측 가능한 난수 시드, PBE 반복 횟수 부족,
비밀번호 하드코딩류. 벤치마크에서 놓친 53건 중 51건이 규칙이 없어서 놓친 것.
config/tier1_rules.json에 규칙을 추가하고 extract_java.py에 잡는 로직을 붙인다.
가장 효과가 크다.

**2. 출처 판별 (확대수사 1층)** — 값 추적이 "못 찾았다"로 끝난 자리에서, 찾다가
닿은 끝이 무엇인지 코드가 판별하는 기능. 셋으로 갈린다:
난수 생성기(SecureRandom)가 채운 값 → 제대로 만든 키니 정상 확정 /
코드에 박힌 상수 배열 → 하드코딩이니 위반 확정 /
환경변수 등 외부에서 오는 값 → "외부에서 옴"이라 적고 확인 필요.
전부 구조 확인이라 LLM 불필요. 설계도의 provenance slice 노드가 이것이다.
현재 "확인 필요" 58건의 상당수가 이걸로 자동 판정된다.

**3. 출처 지목 (확대수사 2층)** — 1층으로도 안 갈리는 소수에서 LLM에게 관련 코드를
읽히고 "값의 출처가 몇째 줄이냐"만 지목시키고, **그 줄을 코드가 다시 열어 검증**한
뒤에만 채택. LLM 답을 그대로 믿으면 원칙 2가 깨진다. 파인튜닝은 불필요하다고
판단됨(먼저 프롬프트로 돌려보고 미상률이 높으면 그때 검토).

**4. Python 지원을 Java 수준으로** — 지금 Python은 직접 호출만 잡는다. 값 추적과
표 비교가 없다. extract_java.py의 구조를 참고해 같은 걸 만들면 된다.

**5. 검색 품질의 정직한 재평가** — 현재 검색 정확도 92%는 평가 문제를 조항
원문에서 베껴 만들어 부풀려진 숫자다. 조항 원문과 무관한 표현으로 평가셋을 다시
만들어 재측정할 것. 그 후 규칙당 고정 1문장인 검색 질의를 판정별 동적 질의로.

**6. 코드 유사도 검색(code_index.py) 연결 여부 결정** — 부품은 있는데 미연결.
쓸 곳은 하나다: 알려진 오용 코드와 "닮은" 함수를 찾아 검사 후보에 추가하는 것
(사내 래퍼, 복붙 변형처럼 규칙 트리거에 안 걸리는 놈들). 단 **후보 추가까지만** —
판정은 반드시 기존 검문(값 추적→표 비교→LLM)을 통과시킬 것. 실제 저장소에서
"이 경로로만 잡힌 확정 건수"를 재보고, 0에 가까우면 빼는 결정도 정당하다.

**7. README 갱신** — 아직 옛 챗봇 시스템 설명이다. 챗봇 부품(ingestion/generation/
persistence/retrieval과 ask·scan·status·rebuild 명령)은 2026-08-30에 걷어냈으므로,
1~3절 내용 기준으로 다시 쓰면 된다.
