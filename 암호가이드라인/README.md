# 수정 방향 — 전체 지도

이 폴더는 현재 RAG를 CryptoMisuse-OSS 파이프라인의 지식 계층으로 바꾸기 위한 수정 계획을 담는다.
진단 근거는 실제 코드 확인과 실측으로 얻은 것이며, 추정으로 쓴 항목은 그렇다고 표시했다.

## 무엇이 달라지는가

현재 저장소는 범용 사내 문서 QA 앱이다. 요구사항정의서에도 "여러 형식으로 보관된 문서를 의미
단위로 검색"이 목적으로 적혀 있고, 암호나 표준문서에 대한 언급은 없다. 잘 만들어진 앱이지만
우리가 필요한 것과 소비자가 다르다.

파이프라인이 요구하는 것은 사람이 질문하는 챗봇이 아니라, 기계가 호출하는 증거 서비스다.
탐지 노드는 구조화된 정보를 넘기고 규칙과 임계값을 받아야 하고, 보고 노드는 지적사항을 넘기고
조항과 축자 인용을 받아야 한다. 같은 입력에 같은 출력이 나와야 하고, 인용한 조항은 원문과
대조 가능해야 한다.

그래서 이 작업은 고장 수리가 아니라 용도 변경이다.

## 현재 상태 요약

확인된 사실만 적는다.

색인 데이터가 하나도 없다. Qdrant 컬렉션 정의(`document_chunks_v1`, 1024차원, `dense` 벡터 하나)만
한 번 생성됐고 벡터는 비어 있으며, 메타데이터 DB 파일 자체가 없다. 되돌릴 데이터가 없으므로
구조를 바꾸는 데 재색인 비용이 들지 않는다. 지금이 손대기 가장 좋은 시점이다.

RAG 프레임워크는 쓰지 않았다. LangChain, LlamaIndex, Haystack 모두 저장소 전체에서 한 건도
검출되지 않는다. 검색과 청킹과 리랭킹 로직 약 8,600줄을 직접 작성했고, 임베딩·리랭커·벡터DB·
파서는 표준 라이브러리를 쓴다. 골격 설계(계층 분리, 의존성 주입, 버전 관리형 색인)는 우리
요구에 오히려 잘 맞으므로 유지한다.

PDF의 표가 읽히지 않는다. 페이지 텍스트를 통으로 뽑기만 해서 표가 행이 아니라 열 단위로
평탄해진다. 실측으로 확인했다. 표 인식 기능을 쓰면 완전히 복원된다.

조항 정보가 없다. PDF 파서가 섹션 경로를 채우지 않아 인용 단위가 파일명과 페이지 번호뿐이다.

스캔 문서의 품질을 검사하지 않는다. 파서의 유일한 검사는 글자 수가 20자 미만인지 보는 것이라,
이미 OCR된 깨진 텍스트가 그대로 통과한다.

OCR이 배선되어 있지 않다. `OCRAdapter`는 색인 흐름 어디에서도 호출되지 않으며, 살리려 해도
`ParsedDocument(**parsed_doc.__dict__)` 형태의 호출이 슬롯 데이터클래스에서 예외를 낸다.

검색이 의미 기반 하나뿐이다. 어휘 검색이 없어서 `SHA-1`과 `SHA-256`처럼 정확한 문자열 구분이
필요한 질의에 취약하다. 설계 문서의 결정 항목 AD-007에 "하이브리드는 named vector로 확장
가능하게 설계한다"고 적혀 있으므로, 원래 계획된 2단계가 아직 오지 않은 상태다.

리랭커가 청크 뒷부분을 보지 못한다. 입력이 512토큰으로 잘리는데 청크는 최대 900토큰이다.

부품이 없으면 조용히 가짜로 동작한다. 임베딩 백엔드가 없으면 모든 문서에 같은 상수 벡터를
주고, 경고 한 줄만 남기고 진행한다.

의존성이 고정되어 있지 않다. 17개가 모두 하한만 지정돼 있고, 코드에서 import하는데 목록에 없는
패키지가 7개다(httpx, pypdf, portalocker, pytesseract, PIL, markdown, numpy).

문서 지문에 MD5를 쓴다. 용도는 변경 감지라 보안 위협은 아니지만, 우리가 만드는 도구가
탐지해야 하는 대상이 MD5다.

## 작업 순서와 근거

순서를 정하는 원칙은 하나다. **뒤 단계가 앞 단계의 출력을 먹으므로, 앞이 틀리면 뒤를 아무리
잘 고쳐도 소용없다.**

1. 문서 품질과 OCR — 텍스트가 깨져 있으면 표를 아무리 잘 인식해도 숫자가 틀린다.
2. 파싱 구조 추출 — 표와 조항이 잡혀야 청킹이 할 일이 생긴다.
3. 청킹과 색인 — 조항 단위 청킹, 구조 헤더, 앞뒤 연결, 어휘 벡터 자리 확보.
4. 검색과 인터페이스 — 하이브리드, 필터 노출, 증거 서비스 API.
5. 평가 — 골드셋으로 1~4의 효과를 숫자로 확인.

평가셋은 4단계가 아니라 1단계와 병행해서 만들어 두어야 한다. 첫 색인을 돌리기 전에 있어야
"표 파싱을 고친 것이 실제로 효과가 있었는가"를 비교할 수 있다.

## 지키기로 한 원칙

**추출한 값은 원문과 대조한 것만 기록한다.** 조항 번호나 임계값을 추정으로 채우지 않는다.
추정으로 채운 조항 번호는 권위 있는 오답이 되고, 이 프로젝트에서 가장 나쁜 실패다.
확인 전 값은 `TBD`로 남긴다.

**LLM이 생성한 텍스트는 색인에 넣지 않는다.** 우리는 축자 인용과 그 해시를 증거로 낸다.
생성 문장이 색인에 섞이면 원문인 것처럼 인용될 위험이 있다.

**판정은 규칙표에서, 서술은 검색에서.** 검색 순위 변동이 탐지 결과를 바꾸면 재현성 지표가
무의미해진다.
