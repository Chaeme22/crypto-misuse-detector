# 1단계 — 문서 품질과 OCR

목표는 하나다. **색인에 들어가는 텍스트가 원문과 같다는 것을 보장한다.**
보장할 수 없는 문서는 색인하지 않고 사람에게 넘긴다.

## 왜 여기서 시작하는가

우리 코퍼스는 표준문서라서 답이 숫자와 알고리즘 이름에 담겨 있다. 키 길이 2048, 보안강도
112비트, SHA-1, AES-256 같은 짧은 토큰이 전부다. 그래서 문자 하나가 깨지면 의미가 통째로
바뀐다.

- `2048` 이 `2O48` 로 읽히면 최소 키 길이 임계값을 뽑을 수 없다.
- `112` 가 `1l2` 로 읽히면 보안강도 매핑이 무너진다.
- `SHA-1` 이 `SHA-l` 로 읽히면 알고리즘 매칭 자체가 실패한다.

이 값들이 그대로 1단계 규칙표의 임계값이 되고, 그 임계값으로 심각도를 매기고, 그 결과가
데이터셋 라벨이 된다. 즉 OCR 오류 하나가 파이프라인 끝까지 전이된다.

그리고 표 인식보다 먼저다. 텍스트가 깨져 있으면 표 구조를 아무리 잘 잡아도 칸 안의 값이 틀린다.

## 현재 무엇이 문제인가

**스캔본을 걸러내지 않는다.** PDF 파서는 페이지 텍스트가 20자 미만이면 OCR이 필요하다고
기록만 하고, 그대로 색인을 진행한다. 텍스트가 전혀 없으면 `"(No text extracted from PDF.
OCR status: required)"` 라는 문자열 하나를 블록으로 만들어 내보낸다. 이 문자열이 청크가 되고
임베딩되고 검색 가능한 상태로 저장된다. 검색 결과로 나올 수 있고 인용될 수도 있는 유령 청크다.

**텍스트가 있으면 품질을 따지지 않는다.** 더 위험한 쪽이다. KISA 구 문서(2008/2013/2014)는
스캔 후 OCR된 형태가 흔한데, 이 경우 텍스트 레이어가 존재한다. 파서의 검사는 글자 수뿐이라
깨진 텍스트가 정상으로 통과한다. 조용히 통과하므로 사람이 알아챌 기회조차 없다.

**OCR이 배선되어 있지 않다.** `parsing/ocr_adapter.py`에 어댑터가 구현돼 있지만 색인 흐름
어디에서도 호출되지 않는다. `ingestion/coordinator.py`에 OCR 참조가 한 건도 없다.

**배선해도 즉시 예외가 난다.** 어댑터가 결과를 합칠 때 `ParsedDocument(**parsed_doc.__dict__,
ocr_status=...)` 형태로 객체를 다시 만드는데, `ParsedDocument`는 `slots=True` 프로즌
데이터클래스라 `__dict__`가 없다. 세 곳에서 같은 방식으로 호출한다.

**설정된 OCR 제공자가 존재하지 않을 가능성이 높다.** 기본값이 `unlimited_ocr`이고 주소가
`localhost:8000`인데, 그 서비스가 떠 있지 않으면 OCR은 실패한다. 로컬 대체 수단인 Tesseract는
설치돼 있지 않고 의존성 목록에도 없다.

## 설계

### 원칙: 통과시키지 말고 막는다

품질을 보장할 수 없는 문서는 **색인하지 않는다.** 지금처럼 빈 문자열이나 깨진 텍스트를
넣어두고 나중에 검색 품질을 탓하는 구조를 없앤다. 막힌 문서는 상태로 남기고 사람이 처리한다.

이미 `DocumentStatus.OCR_REQUIRED`가 열거형에 정의돼 있으나 아무 데서도 쓰이지 않는다.
이 값을 쓴다.

### 판정 기준

문서를 네 가지로 나눈다.

**정상** — 텍스트 레이어가 있고 품질 지표가 정상. 그대로 색인한다.

**OCR 필요** — 텍스트 레이어가 없거나 대부분의 페이지에 텍스트가 없다. OCR을 돌린다.
OCR이 불가능하면 색인을 막고 `OCR_REQUIRED` 상태로 남긴다.

**품질 의심** — 텍스트는 있으나 깨짐 지표가 높다. 색인을 막고 사람 검수로 넘긴다.
자동으로 재OCR하지 않는다. 이미 텍스트가 있는 문서를 자동으로 덮어쓰면 더 나빠질 수 있고,
어느 쪽이 원문에 가까운지는 사람이 봐야 한다.

**부분 스캔** — 일부 페이지만 텍스트가 없다. 해당 페이지만 OCR하고 나머지는 유지한다.

### 품질 지표

`tools/kb_doctor.py`에 이미 구현해 둔 지표를 그대로 쓴다. 색인 파이프라인과 진단 도구가
같은 판정을 내려야 하므로, 로직을 한 곳에 두고 양쪽이 가져다 쓴다.

- 단독 자모 출현율 — 정상 한글 문서에는 거의 없고 OCR 실패 시 급증한다.
- 숫자-문자 혼동 후보 — `2O48`, `1l2`, `SHA-l` 형태. 우리 도메인에서 가장 치명적이다.
- 치환 실패 문자와 사물함 문자 — 인코딩이나 폰트 문제.
- 공백 없는 과도한 장문 토큰 — 레이아웃 붕괴 신호.
- 임베딩 폰트 수 — 0이면 이미지 기반 문서일 가능성.
- 핵심 암호 토큰 검출 수 — 이 코퍼스라면 반드시 여러 종이 나와야 한다.

문턱값은 지금 임의로 정한 값이다. 실제 문서 열한 개를 돌려본 뒤 조정한다.

### OCR 제공자

원격 서비스와 로컬 Tesseract 두 가지가 이미 구현돼 있다. 설정된 제공자가 응답하지 않으면
실패로 처리하고, 자동으로 다른 제공자로 갈아타지 않는다. 어떤 도구로 뽑은 텍스트인지가
증거 추적에 남아야 하기 때문이다. 대체가 필요하면 설정을 명시적으로 바꾼다.

한국어 문서에는 `kor+eng` 조합이 필요하다. 국문 본문에 영문 알고리즘명이 섞여 있기 때문이다.

### 표는 OCR로 복원되지 않는다

스캔본은 표의 괘선이 이미지라서, OCR로 텍스트를 얻어도 행과 열의 구조는 복원되지 않는다.
일반 OCR은 읽은 순서대로 텍스트를 뱉을 뿐이다. 그래서 스캔본에 중요한 표가 있으면 두 가지
중 하나를 택해야 한다. 레이아웃 분석이 가능한 OCR을 쓰거나, 그 표만 사람이 옮겨 적고 출처를
기록한다. 표 개수가 많지 않다면 후자가 더 빠르고 정확하다. 실제 문서를 본 뒤 판단한다.

## 구현 항목

1. 품질 판정 로직을 공용 모듈로 분리하고 진단 도구가 그것을 가져다 쓰게 한다.
2. `ocr_adapter.py`의 데이터클래스 재생성 오류 세 곳을 수정한다.
3. `coordinator.py`에 OCR 단계를 배선한다. 파싱 직후, 정규화 직전이다.
4. 품질 게이트를 넣는다. 판정이 정상이 아니면 색인을 중단하고 상태를 기록한다.
5. 누락된 의존성을 목록에 추가한다.
6. 문서 폴더를 만든다.

## 검증 방법

**합성 문서로 먼저 확인한다.** 정상 텍스트 PDF, 텍스트 레이어를 제거한 스캔본, 숫자와 자모를
일부러 깨뜨린 문서 세 종을 만들어 각각 정상, OCR 필요, 품질 의심으로 판정되는지 본다.
이 검증은 이미 한 번 통과했다.

**실제 문서로 확인한다.** 표준문서 열한 개를 `document/`에 넣고 진단을 돌린 뒤, 판정 결과를
사람이 몇 개 열어보고 맞는지 확인한다. 문턱값은 이때 조정한다.

**통과 기준** — 색인을 돌렸을 때 품질이 보장되지 않은 문서가 하나도 벡터DB에 들어가지 않고,
막힌 문서가 상태 조회에서 이유와 함께 보인다.
