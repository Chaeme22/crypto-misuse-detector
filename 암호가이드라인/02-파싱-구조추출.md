# 2단계 — 파싱과 구조 추출

목표는 **문서의 구조를 그대로 살려서 블록으로 내보내는 것**이다.
표는 표로, 조항은 조항으로, 순서는 순서대로.

## 현재 무엇이 문제인가

### 표가 열 단위로 붕괴한다

PDF 파서는 `page.get_text("text")` 하나로 페이지 텍스트를 통째로 뽑는다. 이 방식은 표를
표로 인식하지 않으므로, 셀이 조판된 순서대로 평탄하게 나열된다. 실측으로 확인한 결과다.

키 길이 표를 모사한 PDF에서 파서가 본 것은 이렇다.

```
Strength / 112-bit / 128-bit / 192-bit / Symmetric / 3DES / AES-128 / AES-192 / RSA / 2048 / ...
```

원래 표는 이렇다.

```
112-bit → 3DES  → RSA 2048 → SHA-224
128-bit → AES-128 → RSA 3072 → SHA-256
```

행 연관관계가 사라졌다. `112-bit` 다음에 오는 토큰이 `3DES`가 아니라 `128-bit`이므로,
"112비트 보안강도의 권고 대칭키는?"이라는 질의에 `AES-128`을 답할 가능성이 높다. 그리고 그
답에 권위 있는 문서의 페이지 번호가 인용으로 붙는다.

PyMuPDF의 `find_tables()`를 쓰면 완전히 복원된다. 같은 파일로 확인했다.

부수적으로, 청킹 쪽에는 표를 행 단위로 정리하는 코드(`_linearize_table_block`)가 이미 잘
구현돼 있다. 그런데 `BlockType.TABLE`을 내보내는 파서가 DOCX/XLSX/PPTX뿐이라, 코퍼스의
100%인 PDF에서는 한 번도 호출되지 않는 죽은 코드다. 파서를 고치면 저절로 살아난다.

### 페이지 하나가 블록 하나가 된다

파서는 빈 줄 두 개(`\n\n`)를 기준으로 단락을 나누는데, PyMuPDF의 텍스트 모드는 그런 출력을
거의 내지 않는다. 실측 결과 단락과 표와 각주가 섞인 페이지에서 블록이 딱 하나 나왔다.

그래서 단락 구조가 사라지고, 매 페이지 반복되는 머리말과 꼬리말이 모든 청크에 섞인다.
표준문서는 페이지마다 기관명과 문서명과 쪽번호가 반복되므로 노이즈가 상당하다. 청킹의 중복
제거는 내용이 완전히 같을 때만 걸러내므로 이건 못 잡는다.

### 조항 정보가 전혀 없다

PDF 파서는 `section_path`를 채우지 않는다. 그 결과 인용이 파일명과 페이지 번호뿐이다.

우리가 필요한 인용은 이런 형태다.

```
NIST SP 800-131A Rev.2 §5.1 Table 5 (p.37)
KISA 암호알고리즘 및 키길이 이용안내서(2018.12) 표 3-2 (p.24)
```

원문 조항을 인용해야 하는 도구에서 인용 단위가 페이지인 것은 미달이다.

### 인용 페이지가 틀릴 수 있다

청킹이 이전 페이지 끝을 문자 단위로 잘라 다음 청크 앞에 붙이는데, 그 청크의 페이지 번호는
현재 페이지로 기록된다. 37페이지 청크 안에 36페이지 문장이 들어 있고, 그 문장이 인용되면
출처가 37페이지로 표기된다. 근거 문서 시스템에서 이건 치명적이다.

### 언어가 한국어로 고정돼 있다

모든 PDF에 `language="ko"`를 붙인다. NIST 영문 문서가 한국어 형태소 분석기를 타고, 저장된
청크의 언어 메타도 전부 "ko"가 되어 언어 필터링이 불가능해진다.

## 설계

### 블록 종류

파서가 내보내는 블록을 세 종류로 정리한다.

**표 블록** — 표 하나가 블록 하나다. 절대 쪼개지 않는다. 캡션이 있으면 함께 담는다.
행은 헤더와 짝지어 자립적으로 만든다.

```
[표] Table 5. Approval status
[Header] 보안강도 | 대칭키 | RSA | 해시
[Row 1] 보안강도=112비트 | 대칭키=3DES | RSA=2048 | 해시=SHA-224
[Row 2] 보안강도=128비트 | 대칭키=AES-128 | RSA=3072 | 해시=SHA-256
```

헤더와 값을 짝지어 두는 것이 핵심이다. 이러면 청크가 잘리거나 리랭커가 앞부분만 읽어도 행의
의미가 유지된다.

**본문 블록** — 표 영역을 제외한 나머지를 블록 단위로 뽑는다. 읽기 순서를 보정하고, 머리말과
꼬리말을 제거하고, 줄바꿈으로 끊긴 문장을 이어 붙인다.

**제목 블록** — 조항 제목. 뒤따르는 블록들의 조항 경로를 결정한다.

### 조항 경로

두 가지 수단을 함께 쓴다.

목차 북마크(`doc.get_toc()`)가 있으면 그것이 1순위다. 제목과 시작 페이지가 나오므로 페이지를
조항에 매핑할 수 있다. NIST와 KISA 문서 대부분이 북마크를 갖고 있을 것으로 예상하나, 실제
문서로 확인해야 한다.

북마크가 없거나 부실하면 본문에서 번호형 제목을 정규식으로 잡는다. `5.1`, `제3장`, `표 3-2`,
`Table 5` 형태다. 국문과 영문 서식이 다르므로 양쪽을 모두 커버해야 한다.

결과는 계층 경로로 저장한다. 예: `("5 Hash Functions", "5.1 SHA-1")`.
이 경로가 나중에 청킹 단위와 인용 단위를 동시에 결정한다.

### 순서 정보

모든 블록에 문서 내 일련번호를 붙인다. 이건 이미 `sequence` 필드로 있으나, 파서가 페이지 통짜
블록만 만들어서 실질적인 의미가 없다. 블록을 제대로 나누면 순서가 의미를 갖는다.

페이지 정보는 시작과 끝을 함께 보존한다. 지금은 첫 페이지 하나만 남기는데, 표가 페이지를
넘어가거나 조항이 두 페이지에 걸치면 `p.36-37` 형태로 인용해야 정확하다.

### 페이지를 넘어가는 표

NIST 표는 두세 페이지 이어지는 경우가 흔하다. 직전 페이지 끝에 표가 있고 다음 페이지 시작에
같은 열 수의 표가 있으면 이어진 것으로 보고 병합한다. 병합하지 않으면 뒤쪽 조각에 헤더가 없어
의미를 잃는다.

현재 설정의 `preserve_page_boundary`가 참이라 오히려 표를 강제로 쪼개고 있다.

### 언어 판정

한글 문자 비율로 페이지 단위 판정한다. 문서 전체를 하나로 보지 않는 이유는, KISA 문서에도
영문 참고문헌이나 영문 표가 섞이기 때문이다.

### 파싱 결과를 파일로 고정한다

파싱과 청킹 사이에 중간 산출물을 둔다. 파싱 결과를 JSON으로 저장하고, 청킹은 그 파일을 읽는다.

이유가 셋이다. 표준문서는 몇 년에 한 번 바뀌므로 파싱은 사실상 일회성 작업이다. OCR이 붙으면
파싱이 비싸진다. 그리고 표에서 뽑은 값은 사람이 검수해야 하는데, 메모리에서 청킹으로 바로
넘어가면 검수할 대상이 없다.

중간 산출물이 있으면 청킹 정책을 몇 번이든 공짜로 바꿔가며 실험할 수 있다. 지금 구조로는
정책 하나 바꿀 때마다 PDF 파싱과 OCR을 처음부터 다시 돌려야 한다.

## 구현 항목

1. 표 인식으로 표 블록을 만들고, 행에 헤더를 짝지어 자립화한다.
2. 표 영역을 제외한 본문을 블록 단위로 뽑고 읽기 순서를 보정한다.
3. 반복되는 머리말과 꼬리말을 검출해 제거한다.
4. 줄바꿈으로 끊긴 문장을 이어 붙인다.
5. 목차와 제목 정규식으로 조항 경로를 부여한다.
6. 페이지 범위를 시작과 끝으로 보존한다.
7. 페이지를 넘어가는 표를 병합한다.
8. 언어를 페이지 단위로 판정한다.
9. 파싱 결과를 JSON으로 저장하는 경로를 만든다.

## 검증 방법

**합성 문서** — 표가 포함된 PDF를 만들어 행 연관관계가 유지되는지 확인한다. 이미 붕괴를
실측했으므로 같은 파일로 전후 비교가 가능하다.

**실제 문서** — 각 표준문서에서 키 길이 표를 하나씩 골라, 파서가 뽑은 행과 원문 표를 사람이
대조한다. 이 대조 결과가 그대로 1단계 규칙표의 임계값 근거가 된다.

**통과 기준** — 표 행의 값이 원문과 정확히 일치하고, 인용에 조항 또는 표 번호가 나오고,
페이지 범위가 실제 위치와 맞는다.

## 구현 결과 (실측)

### 두 경로로 갈린다

문서를 열어 보니 표준문서가 두 종류였다.

**텍스트형** - NIST 세 건. 텍스트 레이어와 목차 북마크가 정상이다.

**벡터 아웃라인형** - KISA 네 건(키 길이 안내서 2018, 키 관리 안내서 2014, HTML5 2015,
SEED 2008). CorelDRAW로 제작되어 글자가 곡선으로 변환됐다. 임베딩 폰트 0종, 텍스트 추출
0자. 목차는 "쪽 1", "쪽 2" 껍데기라 조항 정보가 없다.

벡터형은 스캔본보다 유리하다. 해상도 제한이 없고, 표 셀 배경이 채워진 사각형으로 남아
격자 좌표를 정확히 복원할 수 있다. 셀 영역만 잘라 OCR하므로 레이아웃 추측이 없다.

### OCR 설정 (실험으로 확정)

400 DPI 렌더링에 psm 11(sparse text)이 가장 정확했다. psm 7은 짧은 한글 라벨에서
실패했고, 800 DPI는 오히려 나빠지는 경우가 있었다.

언어 조합은 상보적이다. `kor+eng`는 라틴 문자를, `kor`는 한글을 더 정확히 읽는다.
`NIST(미국)`을 전자는 `NIST(O|=)`로, 후자는 `151(미국)`으로 읽는다. 그래서 두 번 읽고
결과가 다르면 어느 쪽도 고르지 않고 둘 다 남긴 뒤 검수 대상으로 표시한다.

### 검증 결과

NIST 세 건 모두 조항 경로 부착률 92~100%다. 800-57은 2107블록에 표 35개, 제목 205개,
부착률 100%.

임계값이 담긴 표가 정확히 나온다.

```
[13쪽 / 조항: 2 Encryption and Decryption Using Block Cipher Algorithms]
  Algorithm=Three-key TDEA Encryption | Status=Deprecated through 2023 Disallowed after 2023
  Algorithm=Two-key TDEA Decryption   | Status=Legacy use
  Algorithm=AES-128 Encryption and Decryption | Status=Acceptable

[15쪽 / 조항: 3 Digital Signatures]
  Digital Signature Generation | < 112 bits ... RSA: len(n) < 2048 | Disallowed
                               | >= 112 bits ... RSA: len(n) >= 2048 | Acceptable
```

KISA 키 길이 안내서는 표 8개를 복원했다. 알고리즘명과 숫자는 정확하다.

```
[6쪽] 128 비트 이상 | AES-128 AES-192 AES-256 | ... | SEED HIGHT ARIA-128 ... LEA-256
      192 비트 이상 | AES-192 AES-256 | ... | ARIA-192 ARIA-256 LEA-192 LEA-256
      256 비트 이상 | AES-256 | ... | ARIA-256 LEA-256
```

### 판정 규칙 두 가지를 실측으로 얻었다

**헤더를 함부로 정하지 않는다.** 모든 표에 헤더가 있는 것은 아니다. 용어-정의 목록을
헤더로 오인하면 `용어=다음행값` 같은 엉뚱한 짝이 생긴다. 첫 행의 모든 칸이 짧고(40자 이하)
비어 있지 않을 때만 헤더로 인정한다.

**장식 도형을 표에서 걸러낸다.** 표지와 삽화가 표로 잡혔다. 진짜 표는 대부분의 행에서 두 칸
이상이 채워진다. 이 구조 신호가 1차 기준이다. 낱말 비율 검사는 OCR 결과에만 건다. 수식이
많은 표(키 길이 조건)가 낱말 비율에서 잘못 걸러졌기 때문이다.

### 남은 한계

- **벡터형 문서의 본문이 처리되지 않는다.** 현재 표만 복원한다. 본문은 페이지 영역 OCR이
  따로 필요하다.
- **벡터형 문서에 조항 경로가 없다.** 목차가 껍데기이고 텍스트가 없어 제목 인식도 불가능하다.
  OCR로 얻은 제목을 쓰는 경로가 필요하다.
- **한 페이지에 표가 둘이면 하나로 합쳐진다.** 격자 군집이 페이지 전체를 대상으로 하기
  때문이다. 세로 간격으로 분리해야 한다.
- **한글 셀 OCR 품질이 낮다.** 알고리즘명과 숫자는 정확하지만 한글 라벨이 깨진다
  (`대칭키 암호 알고리즘` -> `대징키 OF OF oat 리`).
- **머리말이 헤더 첫 칸을 비우는 표는 헤더 인식이 안 된다.** 병합 셀 때문인데, 정보는
  첫 데이터 행으로 보존되므로 손실은 없다.
