# 최종 확인용 — GitHub 보안 권고(GHSA) 수정 커밋 세트 (2026-10-10, 도구 결과를 보기 전에 확정)

## 고른 방법
1. GitHub 전역 보안 권고 API에서 `ecosystem=maven`이고 CWE가 327, 328, 326, 321, 329, 330, 338, 337, 759, 760, 916, 323, 325,
   780, 1240 중 하나인 권고 96건을 받았다.
2. 참조에 GitHub 수정 커밋 링크가 있는 53건을 남겼다.
3. 수정 커밋이 **자바 운영 코드**(`.java`, 테스트 경로·`*Test.java` 제외)를 고쳤고, 바뀐 줄(+/−)에 암호 API 사용
   (`getInstance(`, `SecretKeySpec`, `IvParameterSpec`, `GCMParameterSpec`, `PBEKeySpec`, `PBEParameterSpec`, `SecureRandom`,
   `Random`, `MessageDigest`, `setSeed`, `KeyGenerator`, `KeyPairGenerator`, `.initialize(`, `Cipher`, `Mac`, `DigestUtils`,
   `SecureUtil`, `KeyStore`)이 있는 권고만 남겼다 → **22건, 파일 217개**.
   - 빠진 31건: Groovy 저장소(jervis), 자바 파일을 고치지 않음, 바뀐 줄에 암호 API가 없음(프로토콜·설정 문제) 등.
   - 남은 22건에도 라이브러리 내부 구현(Bouncy Castle)이나 프로토콜 설정(Tomcat 암호 선호 순서)처럼 이 도구가 다루지 않는 종류가
     섞여 있다. 결과를 본 뒤 빼면 공정하지 않으므로 그대로 두고, 결과 보고 때 종류별로 나눠 적는다.
4. 각 파일의 고치기 전 버전(부모 커밋)과 고친 후 버전을 받았다(401개, 이름이 바뀐 1개 누락).
   서버 `~/final/ghsa_src/<권고>/before|after/`, 목록 `~/final/ghsa_manifest.json`.

수집 스크립트: `ghsa_collect.py`(커밋·패치), `ghsa_manifest.py`(바뀐 줄 번호), `ghsa_fetch.py`(파일 받기).

## 분석 방법
- 권고마다 `before/` 폴더 전체(그 커밋이 고친 파일들)를 한 저장소처럼 검사하고, `after/`도 따로 검사한다.
- 저장소 전체가 아니라 고친 파일만 보므로 다른 파일에서 오는 값은 "확인 필요"로 남을 수 있다(알려진 한계로 보고).
- 판정 경로: 정적 판정, 그리고 배포 모델(v2) 판정 두 가지를 모두 잰다.

## 채점 기준
- **채점 영역**: 바뀐 줄에 암호 API가 있는 파일의, 고치기 전 버전에서 지워지거나 바뀐 줄(±2줄).
- **탐지(넓은 기준)**: 채점 영역에 범위 안 규칙(11개 중 아무것이나)의 위반·경고가 있으면 그 권고를 탐지한 것으로 본다.
- **탐지(엄격 기준)**: 위반·경고의 규칙이 권고 CWE에 대응하는 규칙일 때만 탐지로 본다.
  - 327 → 낡은 암호·ECB·약한 해시·짧은 키·고정 IV / 328 → 약한 해시 / 326 → 짧은 키·약한 키 유도 /
    321·798 → 하드코딩 키·비밀번호 / 329·323 → 고정 IV / 330·338 → 약한 난수·예측 가능한 시드 / 337 → 예측 가능한 시드 /
    759·760 → 고정 솔트 / 916 → 약한 키 유도·약한 해시·고정 솔트 / 325·1240 → 범위 안 규칙 아무것이나
- **확인 필요**만 있으면 따로 센다(엄격·넓은 기준 모두 놓침으로 본다).
- **고친 뒤 확인**: 고친 후 버전에서, 고치며 새로 들어간 줄(±2줄)에 같은 규칙의 위반이 남아 있으면 "고친 뒤에도 경고"로 센다
  (오탐 성격의 지표).
- 권고 하나가 커밋 여러 개면 어느 커밋에서든 탐지되면 탐지로 본다.
