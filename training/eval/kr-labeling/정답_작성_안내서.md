# 국산 암호 사례 — 정답 작성 안내서

동아리원 각자가 **혼자서** 국산 암호 코드 87줄에 정답을 단다. 여러 사람의 정답이 얼마나 일치하는지(일치도) 재고,
다수결로 최종 정답을 정한 뒤 그 정답으로 도구를 채점한다.

---

## 1. 꼭 지킬 것

1. **혼자 판단한다.** 다른 사람과 상의하거나 답을 보여 주지 않는다. (그래야 일치도가 의미 있다)
2. **도구 결과를 보지 않는다.** 이 정답지에는 도구 판정과 연구진 초안이 들어 있지 않다. 다른 곳에서 찾아보지 않는다.
3. **아래 기준대로만 판단한다.** "내 생각엔 괜찮을 것 같다"가 아니라 기준 문장에 맞는지로 정한다.
4. 모르겠으면 억지로 고르지 말고 **판단불가**에 표시한다.
5. 다 끝나면 파일 이름을 `정답지_본인이름.csv`로 바꿔 제출한다.

## 2. 정답지 사용법

파일: `정답지_이름.csv` (엑셀로 열린다). 한 행이 코드 한 줄이다.

| 칸 | 내용 |
|---|---|
| 번호·저장소·파일·줄 | 어느 코드인지 |
| 테스트코드 | `예`면 테스트 코드다. 테스트 코드도 똑같이 기준대로 정답을 단다 |
| 코드 | 판단할 줄 |
| 앞뒤문맥 | 그 줄 앞뒤 6줄. `>` 표시가 판단할 줄 |
| 변수가 정해지는 곳 | 그 줄에 쓰인 변수가 같은 파일 어디서 값이 정해지는지(자동 추출, 빠진 것이 있을 수 있다) |
| **ECB · KEY · IV · HASH · CIPHER** | 해당하는 오용 칸에 `O`. 여러 개면 여러 칸에 `O` |
| **오용없음** | 다섯 가지 중 아무것도 해당하지 않으면 `O` |
| **판단불가** | 주어진 정보로 정할 수 없으면 `O` (메모에 이유) |
| 메모 | 헷갈린 이유, 근거 |

**모든 행에는 반드시 하나 이상 `O`가 있어야 한다**(오용 칸 / 오용없음 / 판단불가 중).
필요하면 GitHub에서 그 저장소의 파일을 직접 열어 봐도 된다(저장소 이름 = `소유자__저장소`).

**중요 — 줄 단위로 판단한다.** 그 줄에서 일어나는 오용만 표시한다. 예를 들어 `BlockCipherMode c = new LEA.CBC();`
줄에는 IV가 없으므로, 다른 줄에서 고정 IV를 넣더라도 이 줄은 IV가 아니다.

## 3. 판정 기준

판정 근거는 우리 지식베이스의 표준 문서(KISA 안내서·NIST 권고)다.

### ECB — 안전하지 않은 운영모드

블록 암호를 **ECB 모드**로 쓰면 해당. ECB는 같은 평문 블록이 늘 같은 암호문이 되어 내용의 패턴이 드러난다.

| 해당 (O) | 해당 아님 |
|---|---|
| `"SEED/ECB/..."`, `"ARIA/ECB/..."`, `"AES/ECB/..."` 처럼 ECB를 명시 | `"SEED/CBC/..."`, `"ARIA/GCM/..."`, CTR, CFB, OFB |
| **운영모드를 안 적은 블록 암호**: `getInstance("ARIA")`, `getInstance("SEED")`, `getInstance("AES")` — 자바 기본값이 ECB | `"RSA/ECB/..."` — 공개키 암호의 ECB는 이름 관례일 뿐 블록 운영모드가 아니다 |
| KISA 참조 구현 `KISA_SEED_ECB.SEED_ECB_Encrypt/Decrypt(...)` | `KeyGenerator.getInstance("ARIA")`, `SecretKeyFactory.getInstance(...)` — 키를 만드는 것이지 암호화 모드가 아니다 |
| LEA 라이브러리 `new LEA.ECB()` | |

### KEY — 하드코딩 키

그 줄에서 쓰는 **암호 키 값이 소스 코드에 적혀 있으면** 해당. 코드를 본 누구나 키를 알 수 있다.

| 해당 (O) | 해당 아님 |
|---|---|
| 키가 문자열 상수: `"myKey12345678901".getBytes()` | 키를 설정 파일·환경 변수에서 읽음: `@Value("${key}")`, `System.getenv(...)` |
| 키가 상수 바이트 배열: `{0x2c, 0x11, ...}` | 키를 메서드 인자로 받고, 같은 저장소에서 상수로 부르는 곳을 찾지 못함 |
| 0으로 채운 빈 배열을 키로 씀: `new byte[16]` | `SecureRandom`·`KeyGenerator`로 만든 키, 키 저장소(KeyStore)에서 꺼낸 키 |
| 같은 파일·다른 파일의 상수(`static final`)에서 가져옴 | |
| 지역 변수에 상수를 넣고 그 변수를 씀 | |

근거: KISA 「암호 키 관리 안내서」(2014) — 키는 생성·분배·보관 절차에 따라 보호되어야 한다.

### IV — 고정 IV(초기화 벡터) · 카운터

그 줄에서 쓰는 **IV(또는 CTR 카운터)가 암호화할 때마다 새로 무작위로 만들어지지 않으면** 해당.

| 해당 (O) | 해당 아님 |
|---|---|
| IV가 상수: `"1234567890123456".getBytes()`, `{0x26, ...}`, `new byte[16]`(0으로 채움) | 암호화할 때마다 `SecureRandom`으로 새로 만듦: `new SecureRandom().nextBytes(iv)` |
| IV를 **설정 파일에서 한 번 읽어 계속 재사용**: `@Value("${iv}")` | 복호화 줄에서, 암호문 앞부분에 붙어 온 IV를 꺼내 씀 (암호화 쪽이 매번 난수로 만든 경우) |
| IV를 **키에서 잘라 내거나 복사**함 (키가 같으면 IV도 늘 같다) | |
| 복호화 줄이라도 암호화와 **같은 고정 IV 변수**를 씀 | |

근거:
- NIST SP 800-38A — "An IV must be generated for each execution of the encryption operation." / "For the CBC and
  CFB modes, the IVs must be unpredictable." / OFB는 매번 다른 값(nonce), CTR은 같은 키의 모든 메시지에서 카운터가
  겹치면 안 된다.
- KISA 「다양한 보안 프로토콜에서의 SEED 활용 가이드라인」(2008) — "초기벡터는 임의로 선택되어야 하고, 예측 불가능해야
  한다."
- 즉 기준은 **"코드에 적혀 있느냐"가 아니라 "매번 새로, 예측할 수 없게 만드느냐"**다. 설정 파일 값이라도 매번 같으면 해당.

### HASH — 취약한 해시

**MD5, SHA-1, MD2, MD4, HAS-160**을 보안 목적(비밀번호 저장, 서명, 무결성 검증)에 쓰면 해당.

| 해당 (O) | 해당 아님 |
|---|---|
| `MessageDigest.getInstance("MD5")`로 비밀번호 해시 | SHA-256 이상, LSH, SHA-3 |
| `Signature.getInstance("SHA1withRSA")` | `Mac.getInstance("HmacSHA1")` — 메시지 인증용 SHA-1은 KISA 표 3에서 허용 |
| | 키 생성·키 팩토리 호출(`KeyGenerator`, `SecretKeyFactory("ARIA")`) — 해시가 아니다 |

근거: KISA 「암호 알고리즘 및 키 길이 이용 안내서」(2018) 표 4(단순해시·전자서명용 해시)에 MD5·SHA-1이 없다.

### CIPHER — 사용 금지 암호 알고리즘

KISA 기준표에 없는 대칭키 암호(**DES, RC4, RC2, Blowfish** 등)를 쓰면 해당.

- **SEED, ARIA, LEA, HIGHT는 해당하지 않는다.** KISA 기준표에 있는 국산 암호다.
- 3DES(DESede)도 이 시험에서는 해당하지 않는 것으로 한다(112비트, 2030년까지 유효 — 도구는 "경고"로 따로 보고).

### 판단불가

- 문맥과 "변수가 정해지는 곳"을 보고, 필요하면 GitHub에서 파일을 열어 봐도 **값이 어디서 오는지 알 수 없을 때**
- 메모에 이유를 적는다(예: "키를 다른 모듈에서 받는데 찾지 못함")

## 4. 예시

| 코드 | 정답 | 이유 |
|---|---|---|
| `KISA_SEED_CBC.SEED_CBC_Encrypt(pbszUserKey, pbszIV, msg, 0, msg.length);`<br>(위에 `pbszUserKey = "abcd1234abcd1234".getBytes()`, `pbszIV = "1234567890123456".getBytes()`) | KEY, IV | 키·IV 모두 코드 상수 |
| `Cipher.getInstance("ARIA");` | ECB | 운영모드 미지정 → 기본 ECB |
| `Cipher.getInstance("ARIA/GCM/NoPadding", provider);` | 오용없음 | GCM은 안전한 모드 |
| `KISA_SEED_ECB.SEED_ECB_Encrypt(seedKey.getBytes(), data, 0, len);`<br>(`seedKey`는 설정값을 복호화해서 얻음) | ECB | ECB 참조 구현. 키는 설정값이라 KEY 아님 |
| `KISA_SEED_CBC.SEED_CBC_Encrypt(key, iv, ...)`<br>(`iv`는 `@Value("${seed.iv}")`) | IV | 설정 IV를 매번 재사용 |
| `KISA_SEED_CBC.SEED_CBC_Encrypt(userKey, iv, ...)`<br>(바로 위에서 `new SecureRandom().nextBytes(iv)`) | 오용없음 | 매번 난수 IV |

## 5. 제출 후 과정

1. 모든 정답지를 모아 연구진이 **일치도**(평가자 간 카파 계수)를 계산한다.
2. 오용 종류마다 **과반수**가 `O`를 준 것을 최종 정답으로 한다.
3. 의견이 갈린 줄(과반이 안 되거나 판단불가가 많은 줄)은 모여서 기준을 다시 보며 확정한다.
4. 최종 정답으로 도구를 채점한다. 보고서에는 "동아리원 N명이 독립적으로 정답을 작성, 일치도 κ = …"로 적는다.
